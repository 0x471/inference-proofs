# ref-serve and ref-recompute: production serving and recompute

These adapters implement the reference baselines from [RFC-0015](../../rfcs/0015-reference-rows.md): production serving (`ref-serve`, SRV-1 to SRV-10, owner decision of 2026-11-09) and recomputation by a verifier with access to the weights (`ref-recompute`, #139). Both share the same pinned engine image, though `ref-recompute` retains its earlier plain-serving configuration via its own `system.yaml` (see §Recompute below). This README documents the engine pin, serving weights, all engine options with links to upstream documentation at the pinned version, and adapter behavior.

## Production serving (`ref-serve`)

To answer how much overhead proving adds under realistic serving conditions, the baseline serves each model the way inference providers serve it: using the pinned engine with default settings, the publisher's release precision, all weights resident in GPU memory, and tensor parallelism across the fewest H200 GPUs required to fit the model (RFC-0015 SRV-6). Overhead compares GPU-seconds per token on both sides (RFC-0004 INV-DERIVE-8).

- **Engine.** Runs vLLM v0.32.0 (see §Engine) through its OpenAI-compatible server (`vllm serve /models --host 127.0.0.1 --port <free port> <engine_args>`), matching how providers deploy it (RFC-0015 Q8; usage context `OPENAI_API_SERVER`). `--host` and `--port` only bind the server to container loopback and do not alter engine settings. Unlike the pre-2026-11-09 adapter, which passed every `EngineArgs` field into the `LLM` class and bypassed both class defaults and server defaults ([entrypoints/llm.py L226 to L227](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/llm.py#L226-L227)), the engine is never constructed from a full `EngineArgs` dump.
- **Options** (SRV-3). Only the allowlisted options below may appear in each `system.yaml` entry (keyed by workload, load point, and GPU count), all documented in [engine_args.md](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/configuration/engine_args.md):

  | Option | Value | Why |
  |---|---|---|
  | `--tensor-parallel-size` | The serving profile's `gpu.count` (4 for Maverick FP8, 1 for Llama 3.1 8B BF16) | Keeps all weights in GPU memory across the fewest GPUs that fit the model (SRV-6, `sizing.py`). |
  | `--max-model-len` | Prompt plus output tokens (1,025, 1,088, or 4,608) | Matches the workload's sequence length. |
  | `--max-num-seqs` | Workload batch size (matched load only) | Enforces the matched batch size (SRV-1). At high load, uses the engine default of 1,024 on GPUs with 70 GiB or more ([arg_utils.py L2933 to L2942](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py#L2933-L2942)). |

  No CPU offload, quantization flag, memory fraction override, `--language-model-only` (RFC-0015 Q4), or `--skip-tokenizer-init` (Q7) is allowed; the engine starts with its full default initialization. Both the validator (schema `system/1` and G2 rule SRV-3) and the adapter itself reject any other option on a serve-role entry.
- **Weights** (SRV-6). Mounted at `/models` from the serving record referencing the workload (`workloads/serving/<id>.yaml`), fetched and verified by `iproofs fetch-model --serving` (RFC-0014 SM-2): Meta's FP8 release of Llama 4 Maverick (via RedHatAI's byte-identical mirror) and Meta's BF16 release of Llama 3.1 8B Instruct (via NousResearch's mirror). Neither mirror includes Meta's `tokenizer_config.json` (RFC-0015 Q7); the first capture records whether the engine starts cleanly without it.
- **Requests** (SRV-2). Sends each batch as a single completions request with the batch's token-ID prompts in `prompt`, `temperature` 0, `max_tokens` equal to the workload's output length, `ignore_eos` true ([sampling_params.py L331](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/sampling_params.py#L331-L333)), and `return_token_ids` true so output token IDs come back in `choices[i].token_ids` ([completion/protocol.py L171 to L178](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/completion/protocol.py#L171-L178); token-in, token-out is tested upstream in [test_token_in_token_out.py](https://github.com/vllm-project/vllm/blob/v0.32.0/tests/entrypoints/openai/completion/test_token_in_token_out.py)). If any request returns a different token count, the job fails with `adapter`.
- **Pre-launch checks** (SRV-3, SRV-6). Before starting the engine, the adapter verifies that an entry exists for the job's load point and GPU count, that `CUDA_VISIBLE_DEVICES` matches `--tensor-parallel-size`, and that every `VLLM_*`, `NCCL_*`, `CUDA_*`, and `TORCH_*` environment variable comes strictly from the base image (`/opt/iproofs/image_env.json`, captured in the Dockerfile before setting any variables, or from the digest-pinned image config in dev installs) or the harness GPU binding (`CUDA_VISIBLE_DEVICES`, `CUDA_DEVICE_ORDER`). Any violation is written to `/io/failure.json` with kind `config` and recorded as such by the harness (RFC-0005 amendment of 2026-11-09).
- **Records** (`/io/commands.jsonl`). Logs the engine command (the runner verifies that it ends with the commit's `engine_args`), the engine environment, the resolved-configuration log line (`Initializing a V1 LLM engine (v0.32.0) with config: ...`, [v1/engine/core.py L134](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/engine/core.py#L134)), the KV-capacity log line (`GPU KV cache size: N tokens, Maximum concurrency for M tokens per request: Xx`, [v1/core/kv_cache_utils.py L2328](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/core/kv_cache_utils.py#L2328)), and `engine_observed` (the installed version, image `VLLM_BUILD_COMMIT`, and batched-token cap from `Chunked prefill is enabled with max_num_batched_tokens=N.`, [config/scheduler.py L307](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/config/scheduler.py#L307)). Full engine output goes to `/io/engine.log`.
- **Placement** (SRV-6). At matched load, if the KV cache holds fewer than `batch × max_model_len` tokens or the engine exits out of GPU memory during startup, the job fails with kind `resource` (attaching the KV-capacity or OOM log line as evidence). Only `resource` failures justify moving a workload to a higher GPU count. At high load, a smaller KV cache logs a warning and lets the engine queue excess requests.
- **Release protocol** (REF-1). After each batch finishes, every request is released as `/io/proofs/req-<i>/outputs.json` (recording `request_index`, `batch`, and `token_ids`) via a temporary name and atomic rename. Outputs are retained for auditing and are never compared against a proving system's outputs (SRV-4).
- **Level 1 ladder** (RFC-0018 CO-4, `load_point: ladder`). Covers `l1-maverick-p512-o512` on `serving-h200x4-hosted` (Meta's FP8 release), `l1-l31-8b-p512-o512` on `serving-h200x1-hosted` (Meta's BF16 release), and `l1-gpt2-p512-o512` on `serving-h200x1-hosted` (OpenAI's FP32 GPT-2 release). A single `prove` call runs the full concurrency ladder over the rung's 1,024 baseline prompts (`baseline.prompts` from `iproofs.level.baseline_prompts`, stored with `batch_size` 1,024 and `batches` 1). The runner copies `ladder`, `warmup_batches`, and `timed_batches` from `levels/L1.yaml` into `job.json`. For each concurrency `c` in ladder order, the adapter sends `warmup_batches` (1) warm-up batches followed by `timed_batches` (3) timed batches of `c` requests, each as one completions request. Batch `s` (counting warm-ups first, `s = 0, 1, ...`) uses ladder prompts `(s × c + j) mod 1,024` for `j < c`, giving each batch `c` distinct prompts without repeating a prompt within any Level 1 concurrency step (`(1 + 3) × 256 = 1,024`). Requesting a concurrency higher than the prompt count fails with `config`. Only `--tensor-parallel-size` and `--max-model-len 1024` are passed; `--max-num-seqs` remains at vLLM's default of 1,024 on 70 to 160 GiB non-A100 GPUs (`get_batch_defaults` in [arg_utils.py](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py) at v0.32.0), which exceeds the ladder's maximum `c` of 256 (higher values fail with `config`). A KV cache smaller than `c × 1,024` tokens logs a warning and queues excess requests. Each batch sets a unique `cache_salt` request field ([completion/protocol.py](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/completion/protocol.py), not an engine option) so prefix caching stays enabled at its default without reusing cached blocks across batches that revisit the same prompts. Outputs are released as `/io/proofs/c<c>-w<k>-r<j>` (warm-up batch `k`) or `c<c>-b<k>-r<j>` (timed batch `k`), with `outputs.json` containing `request_index`, `concurrency`, `batch`, `warmup`, and `token_ids`. If a concurrency step fails or returns an unexpected token count, the adapter logs a warning and stderr message and continues to the next step; if every step fails, the job fails. `iproofs.baseline.full_load` derives serving rates and full-load throughput from the recorded release timestamps.
- **Sizing** (`sizing.py`, grade projected, never published). Estimates the initial GPU count to try based on file sizes, workload shape, and profile GPU memory; it only orders placement attempts and does not determine eligibility.
- **Image.** Built by `Dockerfile` directly `FROM` the digest-pinned vLLM image with an empty `inputs.lock`, since the base image already includes everything production serving needs. The image currently pinned in `system.yaml` was built from `2dacdc85` for plain serving and bakes in an older `system.yaml`, so the runner refuses jobs on it until the `images` workflow rebuilds it and updates the pin (RFC-0014 B7). Because `ghcr.io/ai-verification-observatory/ref-serve` could not be pulled anonymously on 2026-11-09 (RFC-0015 Q6), Hugging Face jobs use the development installer (`dev_install.py`; see `docs/runbooks/hf-jobs.md` §Production serving).
- **Tests** (`tests/`, CPU, INV-ADAPTER-9). Cover pre-launch checks, command logging, output length validation, KV-capacity rules, resolved-configuration comparisons, the release protocol against captured outputs (`tests/fixtures/README.md`), and sizing calculations.

## Engine

- vLLM v0.32.0, released 2026-10-18 at commit `5df63a7203cdb9328d824a27b682e77c7b9928be`, image `docker.io/vllm/vllm-openai@sha256:befccf0e7e4089aa23926bb6f887a85c0d46c2a99e6de5c5ffdf5cb7957c5b34` (manifest list). Selected under RFC-0015 Q1 as the newest stable release meeting requirements on 2026-11-04; as of 2026-11-09, GitHub still listed v0.32.0 as the latest non-prerelease (v0.33.0rc3 being a release candidate).
- For `ref-recompute` only: `vllm-gguf-plugin` v0.0.5 (published by the vLLM project) is installed in the `ref-recompute` image and pinned in its `inputs.lock` (#138), since GGUF support in v0.32.0 lives in that plugin ([gguf.md](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/features/quantization/gguf.md)).
- No patches or changes are made to engine source code (AGENTS.md rule 1).

## Recompute (`ref-recompute`)

`ref-recompute` retains the pre-2026-11-09 engine setup: it constructs vLLM's `LLM` class via the engine's CLI argument parser using the options in its `system.yaml`, loading the workload's own pinned model files under RFC-0015 PM-0 through PM-4.

### Precision per workload (RFC-0015 §Precision matching)

Recompute loads strictly the workload's pinned files (PM-0). Workloads (#49) specify `precision.served` as `W8A8` (integer) for SASH workloads and `UD-Q4_K_XL` for Maverick workloads.

| Workload | `precision_used` | Why |
|---|---|---|
| `sash-l31-8b-c4096`, `sash-l31-8b-c1024` | `fp8`, declared substitution | v0.32.0 only serves INT8 W8A8 from checkpoints pre-quantized with `llm-compressor` ([int8_w8a8.md](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/features/quantization/llm_compressor/int8_w8a8.md)), which would require different weights (violating PM-0). Instead, FP8 W8A8 is quantized online at load time from the pinned BF16 files ([online.md](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/features/quantization/online.md), `fp8_per_tensor`, Hopper listed), matching the bit widths (PM-4). All quantities on these rows set `quality.precision_substituted: true`. |
| `fp-maverick-w1024-b1`, `fp-maverick-w1024-b24` | `UD-Q4_K_XL`, the pinned GGUF files | Loaded through `vllm-gguf-plugin`. The plugin README does not list Llama 4 as tested, and the five weight files (33 GB to 50 GB each at the pinned revision) exceed an 80 GB GPU, so a recorded failure is expected (RFC-0015 §Feasibility on the profile). |

### Engine options

Every flag below is a documented vLLM v0.32.0 engine argument ([engine_args.md](https://github.com/vllm-project/vllm/blob/v0.32.0/docs/configuration/engine_args.md), generated from [`vllm/engine/arg_utils.py`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/engine/arg_utils.py)) and appears verbatim per workload in `systems/ref-recompute/system.yaml`.

| Option | Value | Why |
|---|---|---|
| `--quantization` | `fp8_per_tensor` | Used for SASH workloads only (see PM-4 above). |
| `--max-model-len` | Prompt plus output tokens plus 1 (4,609, 1,089, or 1,026) | Recompute passes prompt plus claimed output as the input sequence, and vLLM requires space for the 1 generated token it produces. |
| `--max-num-seqs` | 1 | Processes one request at a time (RC-2). |
| `--cpu-offload-gb` | 160 | Used for Maverick only, placing weights that do not fit in GPU memory into host RAM. |
| `--skip-tokenizer-init` | | Because the harness passes and reads raw token IDs, no tokenizer is needed; this also avoids extracting a tokenizer from GGUF files. |

### Teacher-forced argmax (RFC-0015 Q3)

`ref-recompute` submits the prompt concatenated with the claimed output as a single token-ID prompt using `SamplingParams(prompt_logprobs=1, max_tokens=1)` ([`sampling_params.py`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/sampling_params.py#L347-L349)). At each position, the engine returns the top-1 token from `torch.topk` over the log-probabilities ([`Sampler.gather_logprobs`](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/v1/sample/sampler.py#L312-L337)), giving the argmax with ties broken according to `torch.topk`.

## Stored attempts (RFC-0015 SRV-10)

The `ref-serve` runs stored under `results/v0.1` (from 2026-11-05) were plain-serving runs executed on the prover profile (`prover-h100-hosted`) using workload weight files: 12 completed SASH-workload runs (online FP8, PM-4) and 8 failed Maverick runs. They remain archived as recorded and do not pair with any system row.
