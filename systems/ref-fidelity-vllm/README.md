# ref-fidelity-vllm: the fidelity reference in vLLM

Under [RFC-0018 FI-9](../../rfcs/0018-level-1-ladder.md#fidelity), whenever llama.cpp at the level's pinned commit cannot run a rung's 16-bit reference model, the reference, its rerun control, and the smaller comparison model run in vLLM instead. Llama 4 Maverick triggers this fallback: llama.cpp v0.9.0 (`cd959bae`) loads the 16-bit GGUF on 8 H200 GPUs but crashes on its first forward operation with `ggml_cuda_compute_forward: MUL_MAT_ID failed ... an illegal memory access was encountered` (verified under `CUDA_LAUNCH_BLOCKING=1`). The crash persisted across `GGML_CUDA_PDL=0`, `GGML_CUDA_DISABLE_GRAPHS=1`, both combined, disabled flash attention, disabled warm-up, batch size 256, and single-slot mode across two different machines, affecting both our own BF16 conversion and Unsloth's BF16 GGUF. By contrast, the 8-bit `Q8_0` file runs cleanly at 16 slots (325 tokens/s). Each merged expert tensor contains 128 × 8,192 × 5,120 elements, overflowing a 32-bit index, which is the likely (though unconfirmed) cause.

## Engine

Uses vLLM 0.32.0 from the same digest-pinned image as the serving baselines (`docker.io/vllm/vllm-openai@sha256:befccf0e…`, build commit `5df63a72`). The entrypoint loads each model once via vLLM's offline engine (`vllm.LLM`) with `dtype="bfloat16"`, `tensor_parallel_size` matching the job's GPU count, `max_model_len` set to the longest prompt plus 512 plus 64, prefix caching disabled, image inputs disabled, and seed 0. Prompts are passed as raw token IDs (with no BOS token prepended, matching llama.cpp's server behavior) with `temperature=0`, `max_tokens=512`, `min_tokens=512`, and `ignore_eos=True` so greedily selected end tokens remain in the reply and generation continues to 512 tokens (RFC-0018). The `rerun` control submits prompts in reverse order and restores prompt order when writing replies, measuring how sensitive outputs are to batching order.

## Calls

`iproofs fidelity run --engine vllm` issues three calls: `info`, `prove` with `call: reference` (loading the publisher's 16-bit safetensors from `/models` to produce both the reference and `rerun` control), and `prove` with `call: other_model` (loading the smaller comparison model). Any control recipe not handled by this image is recorded as failed with its reason. Quantized controls are generated separately via `iproofs fidelity run --part controls` using the `ref-fidelity` image. KL divergence is not computed here because FI-7 requires llama.cpp's base logits on the 16-bit model.

## Teacher-forced pass (RFC-0018 FI-10 to FI-13)

When `teacher_forced` is enabled in the job, the adapter skips free generation and passes each prompt concatenated with the stored reference reply as token IDs using `prompt_logprobs=256` ("Number of log probabilities to return per prompt token", [sampling_params.py](https://github.com/vllm-project/vllm/blob/5df63a7203cdb9328d824a27b682e77c7b9928be/vllm/sampling_params.py#L347-L349)), `max_tokens=1`, and `flat_logprobs=True`, starting the engine with `max_logprobs=256` (overriding the default cap of 20). Entry `j` of `prompt_logprobs` represents the next-token distribution conditioned on tokens `0` through `j − 1`, so entries 512 through 1,023 correspond to the 512 reply positions. Because vLLM places the actual sequence token first followed by the highest-probability tokens, the adapter sorts each position's entries by probability (breaking ties in favor of the lower token ID) and selects the first entry as the top token.

At v0.32.0, `prompt_logprobs=-1` (paired with `max_logprobs=-1`) can return the full vocabulary ("When set to -1, return all `vocab_size` log probabilities"), though its documentation warns this "may cause OOM" (1,024 positions × 202,048 tokens per prompt materialized as Python lists). `prompt_logprob_token_ids` also allows querying specific token IDs as an array. We use neither: FI-12 requests the top 256 tokens from every engine consistently across llama.cpp, vLLM, and the proving systems.

Sequences are submitted in batches of 32. As with free generation, the `rerun` control submits them in reverse order.

On Llama 4 Maverick (8 H200 GPUs, `results/v1.0/teacher-forced/llama-4-maverick/run-vllm.json`, n = 1 run), scoring all 360 prompts took 40 s after a 291 s model load. Because the teacher-forced pass evaluates the entire sequence as a single prefill whereas the stored reference reply was generated token-by-token during decode, 16-bit floating-point arithmetic can order near-tied logits differently between the two paths: the reference's own teacher-forced pass matches its stored reply at a mean of 506.8 out of 512 positions (median 508, n = 360). Among differing positions, an average of 4.4 per prompt differ in both the pass and its rerun, while 1.6 differ in only one. Consequently, the practical agreement ceiling for an honest copy on this rung is around 507 positions rather than 512.
