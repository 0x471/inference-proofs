    The six checks

    How a check works

    Every system we can run at a public pin gets one request: 512 prompt tokens, 512 reply tokens, greedy, every reply token checked. An end token does not stop the reply. A system has passed on a model when all six checks passed there.

    No check attempts a forged proof. Soundness and weight secrecy are not tested: the glyph reports what the publisher's documents state about them.

    Three checks change one thing the verifier must refuse, and the other three test an honest run. A hash of the commitment, prompt and reply, computed from the weights the prover loads, would pass all six. Level 1 keeps such a system from a position, not from the ladder: it would still read passed. What keeps it from a position is its publisher's recorded statement that an accept is the committed model's own greedy reply, or our reading of one, not a test.

    CheckPasses whenFails when

    Run check

    The publisher's prover, as published at the pin, ran 3 sessions from a cold start, and every reply got an accepted proof.

    passes
    The model's prompts are split into 3 slots. Each slot has a complete session: a job from a cold start whose prove call exits 0 with an accepted proof for every request. It is built from the pinned public commit as published there, with no weakening flag.
    fails
    A slot has 5 incomplete runs, or a recorded refusal by the system's own code with a reason about its inputs, or a counted session used a weakening flag.
    cap
    A session that reaches the spending cap, 120 USD on Llama 4 Maverick and 40 USD on the others, stops and is incomplete.
    counted
    A slot counts its first complete session by start time, never one chosen for its figures. A session that missed Verify without weights only for a visible GPU, and was never verified again, gives its slot to the next complete session of the same image and adapter commit that meets the check.

    Model check

    A proof made with one weight changed is not accepted against the original weights' commitment.

    passes
    Proving with one weight changed, against the commitment to the unchanged weights, gives no accepted proof in 3 of 3 trials of the same change. A prove call that makes no proof counts only when its publisher documents, at the pinned commit, that this outcome means the weights are not the committed ones. An honest proof checked against the changed weights' commitment is refused in 3 of 3 trials of the same pair.
    fails
    A trial was accepted, and the system's own command, run outside our adapter, accepted the same changed input.

    Prompt check

    With one prompt token changed, the verifier refuses the proof.

    passes
    With one prompt token changed, at a position set by a seed and new in each trial, the verifier refuses the proof in 3 of 3 trials.
    fails
    A trial was accepted, and the system's own command, run outside our adapter, accepted the same changed input.

    Reply check

    Every proof covers all 512 reply tokens, and with one changed (first, last or one inside) the verifier refuses it.

    passes
    Every accepted proof covers all 512 reply tokens. With one reply token changed, the verifier refuses the proof at the first position and at the last, 3 of 3 trials of the same change each, and at an interior position set by a seed, new in each of 3 trials.
    fails
    A proof covered fewer than 512 reply tokens, or a trial was accepted and the system's own command, run outside our adapter, accepted the same changed input.

    Verify without weights check

    The verifier reached every verdict with no copy of the model and no GPU.

    passes
    Every counted verdict comes from a verify call with no GPU visible and no file of the model on its filesystem, and the trace of the files it opened names none. A verdict reached with a GPU visible counts when the same proof, verified again in the run's image on a host with no GPU, is accepted under these conditions.
    fails
    The trace names a file of the model, or a verify call needed one.

    Fidelity check

    The proved replies match the original's opening tokens better than the bar (a damaged copy of the model) does, by a paired test at p < 0.05.

    passes
    The replies the counted sessions proved score above the bar, by a paired one-sided sign-flip test at p < 0.05.
    fails
    The bar scores above the replies, by the same test. With neither shown, the check is not decided.
    score
    For one reply, the number of leading tokens equal to the original's reply to the same prompt, 0 to 512. The original is a Hub copy of the model publisher's release, at the publisher's precision, named with its commit on each system page: 16‑bit for Llama 4 Maverick 17B-128E Instruct and Llama 3.1 8B Instruct, 32‑bit for GPT-2.
    bar
    Among the damaged controls that every honest control scores above, the one with the highest mean score. The honest controls are the original run again and its 8-bit and 4-bit copies (Q8_0, Q4_K_M). A system's page lists the damaged ones. With none, the model has no bar and the check is not decided on every row.

    Checks not decided

    Not decided is not failed: a row short of passing only because checks are not decided reads Not passed yet.
    system limit
    The system cannot do what this test needs (its publisher's words are quoted), so the row cannot pass.
    not run
    Not run yet.
    not resolved
    The test ran, and its result does not count yet.
    not reproduced
    A verifier accepted a changed input in our adapter; not yet repeated with the system's own command.

    Figures

    Cost vs serving

    multiple
    m over b, on one model. GPU time counts only the H200 GPUs bound to the job.
    m
    GPU-seconds per proved reply, generation included: the mean of 3 sessions. Proofs released within 1 s of the previous one form a release group. m runs from the first group's last release to the session's last, over the replies released after it. Where a system generates all its replies in a phase of its own, m adds that phase's GPU-seconds over the session's replies.
    b
    GPU-seconds per reply when the same request is served without a proof. The model publisher's own release (FP8 on Llama 4 Maverick) runs on the pinned engine and the fewest H200 GPUs that hold it, at full load. Full load is the lowest concurrency, doubling from 1 to 1,024, whose rate reaches 95 % of the highest. If that is 1,024, the model has no b (not saturated).
    whole sessions
    A row has m when each of its 3 sessions has at least 3 groups after the first, each group's time per reply within 5 % of their median. Otherwise it has no multiple and prints its session GPU-seconds per reply over b, labelled “whole sessions of N replies”.
    parts
    Where a system generates its replies in a phase of its own, two parts print beside the figure, each over b: generation, and the rest (proving under m, commit and proving under whole sessions). The order reads the figure, never a part.

    Tokens per second

    The request's 512 reply tokens over the GPU-seconds one reply took, on one GPU, printed in tokens/s per GPU with the GPU named. Proved: over whole sessions, as Cost vs serving counts them. Served: the same reply served without a proof, at full load, on the same GPU type. Served over proved is Cost vs serving.
    Both depend on the GPU, so neither ranks a row: the order reads m, the steady multiple (OR-3), never a rate.

    Cost per reply

    steady
    m in USD, at the release's price for one H200 GPU-hour.
    session
    GPU-seconds from the start of commit to the release of the session's last proof, over its replies, generation included, in USD at the same price: the mean of 3 sessions.

    Verify time per reply

    The wall time of the verify calls on a session's proofs, summed, over the session's replies: the mean of 3 sessions. A second verify never replaces the session's own time.

    Proof size per reply

    The bytes of every file of a session's proofs, as stored, over the session's replies. A proof that covers several replies is counted once. The mean of 3 sessions, in MB (1 MB is 1,000,000 bytes).

    Fidelity figure

    The share of reply positions where the system's top token is the original's reply token, when the system is fed the prompt and then that reply token by token. It is the mean over the prompts, as a percentage, with 0 for a prompt the system's own code declines. The model's 8-bit and 4-bit copies' percentages (Q8_0, Q4_K_M) are printed under it.
    Computed by the system's own code on the reference reply, not by the proved computation. It sets no state.
    Why top-token agreement: a greedy reply is the top token at each position, so this counts how often the proved model makes the original's choice, at every one of the 512 positions, not only up to the first difference.

    KL to the original weights

    Mean KL divergence per scored token, in nats, of the file the system commits against the original, over 64 texts of 512 tokens. Computed by llama.cpp on the committed file, not the proved computation. It gates nothing.
    not measured
    Printed with the reason where llama.cpp cannot run the original (Llama 4 Maverick's 16-bit file), or cannot load the committed file and the system's adapter returns no distributions of its own.

    Order

    ranked
    Only systems that passed on a model are ranked.
    unranked
    A system that passed is ranked only if its publisher states, at the pinned commit, that an accept means the reply is the committed model's own greedy reply to the prompt, or is read as stating it (marked read as, with its quotes), and the level file records a numeric security level that its publisher states there, for at least one verifier it ships. Otherwise it is listed as Passed, not ranked, with the reason. Level 1 sets no minimum level.
    above
    One system is placed above another when both have a multiple, its mean multiple is at least 10 % lower, and its highest session m is below the other's lowest. A system with a multiple is placed above one without. Two systems without one compare the same way, on session cost per reply.
    position
    1 plus the number of systems placed above it, so equal counts share a position. It is printed beside the count of systems run on that model.
    below
    Under the ranked systems: passed and unranked, then not passed, each group in alphabetical order. A system that has not passed prints its checks and figures and has no position.
    largest model with a passed row
    The largest model, by total parameters, with at least one system that passed and whose publisher states that an accept is the model's own reply.
    glyph
    The glyph never moves a position.
    models
    Nothing is ranked across models.

    Glyph

    The glyph shows how close a row is to a perfect prover, one petal per property. Petals are never added up. Four petals are read from the publisher's documents at the pinned commit. Fidelity is measured by our fidelity run, and is not decided whenever the Fidelity check is. A failed check sets Failed on the petals whose claim it contradicts, a check not decided lowers none, and a passed check raises none. On any doubt the lower step wins.

    Each system page prints its next step, computed from this table.

    Integrity

    soundness

    Can a provider get a reply accepted that the committed model did not compute? Integrity grades the chance of that, as the publisher states it, and whether the statement covers what this row runs. It protects the customer. Met: a proved chance of at most 2^-128 (128 bits) that covers this row.
    protects
    the customer
    question
    The bound the publisher states on a false reply being accepted: whether it is proved, and whether it covers what the row runs.
    Met
    A proved bound that covers what this row runs, every exponent 128 or more.
    Mostly met
    The same with every exponent 100 or more, or Met resting on our reading.
    Partly met
    Any other stated bound above Not met: conjectured, not shown to cover what this row runs, or an exponent from 80 to 99 on a proved bound.
    Not met
    The bound holds only against a weaker prover, has an exponent under 80, or has an exponent under 100 and is not proved.
    Not stated
    No bound with its exponents in the documents read at the pinned commit.
    Failed
    Our Model, Prompt or Reply check failed.
    Not decided
    We have not read the publisher's documents at this row's commit.
    covers what this row runs
    The bound holds for the row's parameters, against any prover, per reply (or per proof with one reply a proof), with each reply checked alone. The publisher's or our records show its conditions hold for the row's files, and the verifier program the row runs is proved or stated to implement what the bound is about. A batch size not recorded is not covered.
    exponent
    In 2^-t, the t: a larger exponent is a smaller chance. An error term q/2^t also has exponent t. Exponents are read as the publisher states them, and no bits figure is computed.
    Not graded here: completeness. Integrity grades soundness only; completeness is what the Run check tests.

    Confidentiality

    zero knowledge of the weights

    Does checking a proof reveal the model's weights? Confidentiality grades what the publisher states and proves about keeping them secret. It protects the provider. Met: zero knowledge proved for what this row runs.
    protects
    the provider
    question
    What the publisher states and proves about a proof showing nothing of the weights' values.
    Met
    A zero-knowledge theorem proved for the configuration this row runs, batch size included, and stated for its programs. A published list of what stays visible, with nothing on it that depends on the weights.
    Mostly met
    A zero-knowledge theorem is proved and a condition of Met is missing.
    Partly met
    The publisher states that the weights stay hidden and proves no zero-knowledge theorem.
    Not met
    The verifier is given the weights, or the publisher states that they are not hidden.
    Not stated
    The documents read say nothing on hiding the weights.
    Failed
    Our Verify without weights check failed.
    Not decided
    Not read at this row's commit.
    Not graded here: hiding the architecture. Level 1 models are open-weights, so their architecture is public; a closed-weights level would grade it.

    Fidelity

    quantization error, in matched leading tokens

    Is the model that is proved as good as the one its publisher released? Proving usually runs a copy whose numbers are stored in fewer bits (quantization). Fidelity compares its replies with the original's, using our 8-bit and 4-bit copies as yardsticks. It protects the customer. Met: shown closer to the original run again than to the 8-bit copy.
    protects
    the customer
    question
    How close the proved replies stay to the model publisher's own release, against the model's 8-bit and 4-bit copies.
    Met
    Replies shown above halfway between the original run again and the 8-bit copy, in a fidelity run of one request at a time.
    Mostly met
    Replies shown above halfway between the 8-bit and the 4-bit copy.
    Partly met
    • The Fidelity check passed, and the replies are not shown above halfway between the 8-bit and 4-bit copies.
    • Or no claim card is found, or its policy accepts tokens other than the model's top token.
    • Or a copy a halfway point needs did not run, failed, or was scored on another number of replies.
    Failed
    The Fidelity check failed: the bar, a damaged copy, scores above the replies.
    Not decided
    The Fidelity check is not decided, or no fidelity record is stored.
    halfway
    The average of two copies' mean scores.
    shown above
    The Fidelity check's paired sign-flip test gives p < 0.05 for the row's scores against the halfway point.
    measure
    Graded on matched leading tokens, as the Fidelity check is. The Fidelity figure is top-token agreement and sets nothing.

    Formally verified

    machine-checked soundness proof

    Has a computer checked the mathematical proof that false replies are refused, and does that check reach the code this row runs? It protects the customer. Met: the verifier code this row runs is machine-checked.
    protects
    the customer
    question
    How far a machine-checked proof of soundness reaches: part of the protocol, an abstraction of it, the protocol with the model, or the verifier code the row runs.
    Met
    Built: the verifier code this row runs, from the bytes it reads to its verdict, with its trusted base listed and no input-reading code outside the proof.
    Mostly met
    Built: the protocol, model included; or the verifier code this row runs, with a gap in its trusted base or its input-reading code.
    Partly met
    Built: an abstraction of the protocol (the protocol without the model, or the model without the protocol), or part of the protocol. A theorem whose conclusion is not about the model, or a build with axioms beyond its tool's standard ones, also stops here.
    Not met
    The publisher states that nothing is machine-checked.
    Not stated
    The documents read name no machine-checked proof.
    Failed
    Our build of the named theorem failed or reported axioms other than the declared ones; or our Model, Prompt or Reply check failed where the stated step is Met.
    Not decided
    A machine-checked proof is stated, and our build of it is not recorded yet; or not read at this row's commit.
    build
    Each step above Not met needs a matching build of the named theorem: one recorded at the pinned commit with the publisher's toolchain. Level 1 reads that record and makes none.
    above Partly met
    Needs a theorem whose conclusion is about a reference definition of the model, and a build that reports only its tool's standard axioms (for Lean, propext, Classical.choice and Quot.sound), so no sorry. The petal's reason prints the most a build could give, and that no outside reader of the proof has reviewed the statement.
    the code
    Only the verifier this row runs counts as the code. A verified verifier the row does not run counts at the protocol level.
    protocol or code
    A proof about a formal model of the method, rather than about a program, verifies the protocol, not the code. Level 1 says the protocol, model included, when that formal model includes this model's computation, and an abstraction of the protocol when it leaves the computation out (or covers the model without the method). Only a proof about the verifier program this row runs verifies the code.
    scope card
    Printed under a system's petals, it sets no state: the petal grades soundness only. Soundness is the verifier's and zero knowledge the prover's, so the cells that ask them of the other party do not apply.
    Not graded here: prover code. Prover code bears on completeness and zero knowledge; the scope card prints what is verified for it, and it sets no step.

    Trust assumptions

    trusted setup or party

    Does checking a proof rely on anyone's honesty besides the mathematics, such as whoever ran a one-time setup or holds a hardware maker's key? It protects the customer. Met: nothing to trust but cryptography, as the publisher states.
    protects
    the customer
    question
    What checking a proof relies on besides cryptography: a setup secret, a fixed set of parties, or a hardware maker's or another trusted key.
    Met
    The publisher states that soundness rests on cryptography alone: no setup made a secret. Met also needs proof files anyone can check, unless the publisher is silent on who can check them.
    Mostly met
    An open setup ceremony with a public transcript, safe if one participant was honest; or Met's facts read by us, not stated in words.
    Partly met
    One honest party among a fixed set, or a challenger within a window; or proofs only a designated verifier can check.
    Not met
    A setup run by one party, a hardware maker's key or another trusted key.
    Not stated
    The documents read say nothing on what soundness rests on.
    Not decided
    Not read at this row's commit.
    This petal does not grade which model a commitment names.

    Why a petal is low or not decided

    not stated
    Not statedNot stated (drawn as an outline): the publisher's documents read at the pinned commit are silent on the property. A guarantee nobody states is graded as none, never as not decided.
    below Partly met, as the publisher states it
    Not metNot met or Failed (drawn filled, name struck): the publisher states that the property does not hold, or what it states falls below Partly met.
    a check failed, or the proof build failed
    FailedNot met or Failed (drawn filled, name struck): a check failed, or the matching build of the publisher's machine-checked proof failed or reported axioms other than the declared ones.
    not read yet
    Not decidedNot decided (drawn hollow): our record of the publisher's documents is missing, in another form or read at a commit other than the one the row runs, or the row has no recorded commit. Not read is not silent: it is not decided, never Not stated.
    Fidelity check not decided or not recorded
    Not decidedNot decided (drawn hollow), Fidelity only: the Fidelity check is not decided, or the row has no fidelity record or no scores.
    waits on our build of the publisher's machine-checked proof
    Not decidedNot decided (drawn hollow), Formally verified only: the publisher states a machine-checked proof, and no build of the named theorem is recorded at the pinned commit with the publisher's toolchain. None can match where the publisher names no toolchain.

    Our reading

    At least one fact behind the petal's step is our reading, not the publisher's words. The petal says “read as”, the publisher's quotes are printed with it, and it is graded Mostly met at most, for every system alike. The name of a construction is never read as a claim.

    Systems not run

    A system with no row is listed after the ladder with one reason: the first of these that holds in its sources, in this order. Each system's line is the fact that sets its reason, linked to where we read it.

    Another kind of check

    It makes no proof. Its check is an attestation, a re-execution, a dispute game or a fingerprint.
    opML
    A fault proof: “the challenge game and single step verification”. (new tab)
    Private ML SDK
    Its check is a signature over the sha256 of the HTTP request body and of the HTTP response body; it makes no proof. (new tab)
    Tinfoil
    Its check is a hardware attestation, as its attestation architecture page describes; it makes no proof (read 2026-11-08). (new tab)
    TOPLOC
    A fingerprint of the activations, not a proof: its validation “Validates against predefined error thresholds”. (new tab)
    Verde (with RepOps)
    A re-execution: “we design Verde, a dispute arbitration protocol”. (new tab)

    A different statement

    It proves a statement other than Level 1's: that a reply is the committed model's own greedy reply to a prompt the verifier is given.
    VerInf
    It “certifies an observed output stream against a committed integer model”, “proving similarity rather than exact reproduction”. (new tab)
    zkGPT
    Its paper leaves the reply out of the proof, Appendix A: “we omit proving the final linear projection and the token generation procedure” (read in the archived copy of 2025-09-02). (new tab)

    No public verifier

    No public code to pin, or no public program that checks a stored proof apart from the prover against a commitment the verifier is given. A prover and verifier that run only together, and a verifier that reads the commitment from the proof file, are both this case.
    Attestable prover
    No public code: its blog post describes “a standalone CPU verifier” and links no repository (read 2026-11-15). (new tab)
    DeepProve
    Its verifier, deep-prove-cli verify, takes one argument, the proof file, and checks the proof against the verifier key inside that file; no documented step makes the key from the weights alone (read at 9d1a53e2). (new tab)
    JOLT Atlas
    Its one program, the prove example, “proves and verifies any model in the zoo”; no program at 329b21ef verifies a stored proof on its own. (new tab)
    NanoZK
    No public code: its paper names no repository (read 2026-11-15). (new tab)
    zkLLM
    An interactive proof: “the prover and verifier works are implemented side-by-side for each component”. (new tab)
    zkPyTorch
    No public code: its paper and its page at polyhedra.network name no repository (read 2026-11-08). (new tab)

    Licence

    No licence file, or a licence that grants no use. A licence that grants internal use for testing and evaluating is read as covering runs we make ourselves; it grants no right to hand the software to anyone else.
    EZKL
    No licence file at the root of the repository at e196b111. (new tab)
    JSTprove
    Its licence: “NO USE RIGHTS ARE GRANTED BY THIS LICENSE.” (new tab)

    No configuration at the request

    No configuration its sources name proves a reply to the Level 1 request on a Level 1 model.
    LuminAIR
    Its README proves a graph run and names no language model (read at 9026bd3d). (new tab)
    Remainder (Community Edition)
    A general GKR prover; its README names no model or language-model circuit (read at 5687fe7f). (new tab)
    ZKML
    Its README proves a model run and names no output tokens; the language model it names is a distilled GPT-2 (read at 43789582). (new tab)
    ZKTorch
    Its README proves a model run and names no output tokens (read at 63b9c689). (new tab)
