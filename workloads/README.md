# Workloads

Each workload is defined in its own file at `workloads/<id>.yaml`, validated against `schema/workload/1.schema.json` ([RFC-0003 §Workload file](../rfcs/0003-workloads.md#workload-file)). Model weights are never committed to this repository; instead, each workload pins them by public source, commit revision, and per-file SHA-256 hash.

`iproofs.workloads.load_workload` validates each file against its JSON schema and then checks several invariants that JSON Schema cannot express. Any violation raises a `config` error identifying the offending field:

- The filename must match `id`, and `version` must match the requested version if one was specified.
- INV-WL-4: `prompts.count == shape.batch_size * shape.batches_per_session` and `prompts.length_rule.prompt_tokens == shape.prompt_tokens`.
- `shape.context_window >= shape.prompt_tokens + shape.output_tokens - 1`.
- `model.tokenizer_file` must appear in `model.files[].path`, or match `file.path` in `model.tokenizer_source` when the tokenizer is pinned from a separate repository.
- Every system ID listed under `systems` must have a corresponding `systems/<id>/system.yaml`.
- When `precision.weight_bits` has basis `file_size`, it must reference files from `model.files` and omit a hardcoded `bits` value; the loader computes it as total bytes × 8 / `model.parameters.total` ([RFC-0003 §Weight bits](../rfcs/0003-workloads.md#weight-bits)).
- When `precision.weight_bits` has basis `computed`, it must reference files from `model.files`. Its recorded `bits` value is verified whenever the files can be inspected: `iproofs fetch-model` reruns its `method` on the verified files, `iproofs fetch-model --headers-only` checks it using HTTP range requests over file headers, and CI verifies it against the stored headers in `harness/tests/fixtures/gguf/` (RFC-0003 WB-5).

The JSON schema itself enforces the closed-division rule (`claim_class` must be present if and only if `division` is `closed`), greedy decoding, and full 40-character hexadecimal model revisions. For closed workloads, the runner also verifies that the job's claim card matches the workload's class (see Closed workloads below).

Each workload pins the exact model referenced by the corresponding system's own runs. SASH's recorded runs use the ungated mirror `unsloth/Llama-3.1-8B-Instruct` at commit `4699cc75b550f9c6f3173fb80f4703b62d946aa5`. A system is added to a workload's `systems` list once its `system.yaml` is merged (the loader requires a `system.yaml` for every ID listed), and a job will only run if the system's own `system.yaml` also lists that workload under `workloads`.

Every workload specifies `precision.weight_bits`, representing the bits per weight in the precision actually proved, along with its source (RFC-0003 §Weight bits). The Maverick workloads record 4.83916475612899 with basis `computed` (via `gguf-active-mean/1` from the pinned GGUF tensor tables, counting mean storage bits per active weight including block scales, with routed experts weighted 1 in 128) and `covers: all`, allowing RFC-0004 to sort their D-SPAB-S metric. The SASH workloads and the closed `l31-8b-c1024` workload record 8 with basis `stated` (from SASH's quantizer for weight matmuls, counting the int8 code without per-channel scales and omitting the embedding table and RMSNorm weights) and `covers: part`. Because the underlying files are BF16 and quantized only at load time, the proved bit width cannot be read directly from the checkpoint files, so RFC-0004 leaves those rows unsorted (RFC-0003 Resolved Q5). RFC-0004 D-SPAB-S divides prover time by active parameters multiplied by these weight bits. The runner copies both values into each run's `inputs`, ensuring that a future correction to `bits` (which bumps the workload version) never retroactively alters a stored run (WB-4).

## Closed workloads

A closed workload defines a shared task with a single fixed `claim_class`: only systems whose claim card matches that exact class can run it, allowing direct comparison across their rows ([RFC-0003 §Divisions](../rfcs/0003-workloads.md#divisions)). When resolving a job, the runner checks the class against the claim card recorded in the manifest (`claims/default.yaml` if present, otherwise `claim.yaml`, since v0.1 jobs do not specify a configuration). A mismatched class, or a proving system lacking a card, raises a `config` error before any container starts (`iproofs.runner.check_card_class`). Reference systems have no claim card (RFC-0015) and skip this check.

[`l31-8b-c1024`](l31-8b-c1024.yaml) is the shared Llama 3.1 8B workload (owner decision, 2026-11-08; [RFC-0003 §Closed workloads](../rfcs/0003-workloads.md#closed-workloads)). Its rows enter a release only once at least two systems with the matching claim class have run it through their adapters without upstream patches (RFC-0003 Q7). `iproofs release freeze` enforces this threshold, failing with a `config` error if fewer than two eligible proving systems have completed runs (`iproofs.release.closed_workload_failures`). Its design choices are documented in RFC-0003 §Decisions:

- **Model.** Reuses the exact files from `sash-l31-8b-c1024` (same repository, revision, file list, and `model.digest`: `sha256:368b6c2838f66f92d67f24276a2314c7c2014b059a33c33ea35d793740377ee7`), so weights fetched for SASH's native workload work here as well. RFC-0003 §Model fetch and hash rule permits this reuse because the digest identifies the files rather than the workload.
- **Precision: W8A8.** The only system with an adapter for this model proves W8A8 (`sash-l31-8b-c1024`), and no other reviewed system states W8A8 support for it (see the table below). Systems proving a different precision run this model in the open division.
- **Shape: 1,024 prompt + 64 continuation positions, batch 1, one batch per session, phase `both`, greedy.** Matches `sash-l31-8b-c1024`, the shorter of SASH's two native shapes (the other is 4,096 + 512). Upstream SASH has no recorded run at this shape, so its geometry is "not stated" ([`systems/sash/README.md`](../systems/sash/README.md#the-two-v01-shapes)). No other system influenced this choice: FlashProve's 1,024-token window covers the entire request context on Llama 4 Maverick ("A request contains a window of T tokens", [`docs/limits.md` L213](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/limits.md?plain=1#L213); "one full-size model shape: that of Llama 4 Maverick, with a window of 1,024 tokens", [L2479-L2480](https://github.com/anthropics/FlashProve/blob/9e2bdd8ff5bf9c62f18263d7dac189b0400b260c/docs/limits.md?plain=1#L2479-L2480)), whereas this workload uses a 1,088-token context on a different model and a different claim class.
- **Claim class: `greedy-continuation/exact-match/committed-weights`**, matching SASH's claim card ([`systems/sash/claim.yaml`](../systems/sash/claim.yaml)). FlashProve's claim card uses `next-token/exact-match/committed-weights`, so if FlashProve ran on this model it would belong in the open division.
- **Prompts.** Drawn from the shared corpus using `corpus-window/1`, with one prompt per job. Because the pinned tokenizer file matches SASH's native workload, `iproofs prompts build l31-8b-c1024 --seed S` produces the same digest as `sash-l31-8b-c1024` for any given seed `S`.

The `systems` list includes `sash`, `ref-serve`, and `ref-recompute`, though none of their `system.yaml` files list `l31-8b-c1024` yet, so no jobs run on it today. Adding it to SASH requires a new adapter image because its `info` output declares supported workloads via `WORKLOADS` in `systems/sash/entrypoint`, and the reference systems each need a `workloads` entry declaring their precision substitution (RFC-0015 PM-0).

## Checking a prompt set

Running `iproofs prompts build WORKLOAD --seed SEED [--out prompts.jsonl]` reconstructs the exact prompt set used by a job for a given seed without running a prover. It fetches and verifies the corpus, loads the workload's tokenizer (either from the verified model cache or by fetching it separately and checking its SHA-256), runs `corpus-window/1`, writes `prompts.jsonl`, and outputs `{workload, seed, count, digest, tokenizers_version}` as JSON. The resulting digest matches `workload.prompt_set_digest` in any manifest recorded with that seed. Real tokenizer files require the `[prompts]` extra (`uv sync --extra prompts`). Because different versions of the `tokenizers` library can tokenize text differently, a version mismatch will appear as a digest mismatch (RFC-0003 §Failure modes).
