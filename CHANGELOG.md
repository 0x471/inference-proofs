# Changelog

All notable changes to the harness, schemas, and methodology are recorded here. This file follows [Keep a Changelog 1.1](https://keepachangelog.com/en/1.1.0/), with an added `Methodology` section for methodology updates referencing their RFCs ([docs/spec/09-release-and-versioning.md §CHANGELOG discipline](docs/spec/09-release-and-versioning.md#changelog-discipline)).

Every pull request that changes the public API, a schema, or the methodology adds an entry under `Unreleased`. Entries state plainly what changed, and every number includes its labels (AGENTS.md rule 2).

### Changed

- Updated the FlashProve adapter's `verify` step to map `cp_verify` exit code 1 to `reject` only when its final line matches the documented `NO: <name>` format, mapping `NO: internal-*` to `no_verdict` and treating any other exit-1 final line as an adapter failure. All stored rejections end with `NO: proof-refused`, so no stored outcome changes.
- Added `iproofs release board v1.0 --check` to CI's validate job so the committed board must recompute byte-for-byte from `results/`.
- Updated `board/1` in place (RFC-0012 amendment of 2026-11-13): every petal now requires `step`, `cause`, and `lowered_by`; the fourth petal is `machine_checked` (carrying `formal`); Weights hidden carries `visible`; `basis` is `statement` or `test`; and petals may include `reading: true` when their decision relies on a reviewer reading (which carries a note). Because no release is frozen yet, the single stored board (`releases/v1.0/board.json`) was recomputed by `iproofs release board` in the same change without altering the meaning of any stored record.
- Sped up `iproofs validate` (RFC-0013) by building the schema registry once per process and parsing each unique YAML payload once, reducing `validate --all` on the v0.1 tree from 25.6 s to 13.5 s (wall time, single run each on one development machine). Single-file checks (G2 schema validation, G3, and G9) now cache results in the user's cache directory keyed by the file's SHA-256 digest, checker source, schema tree, and parser versions, dropping repeat runs on the same machine to 3.0 s (one run). CI runs without a cache, `--no-cache` disables caching locally, and release freezes never read the cache.
- Optimized model verification at job start (RFC-0014 §Model fetch and verification, step 6) to read each file once instead of twice and hash up to 8 files concurrently, producing identical digests.
- Removed unused dataclasses from `iproofs.model` (RFC-0012 §Python loading) for document types no code instantiated (`run/1`, `manifest/1`, `controls/1`, `controls-part/1`, `controls-seed/1`, `release-index/1`, `adapter-job/1`, `target/1`, `external/1`, `criteria/1`); those documents continue to be validated as trees against their schemas.
- Updated CI (RFC-0013) to use three test shards per Python version instead of six, run tree gates once per job rather than twice on pull requests, and remove the nightly workflow (which only repeated `validate` on an unchanged tree and ran a weekly link check invoking a module retired with G12).

### Methodology

- [RFC-0008](rfcs/0008-negative-controls.md) INV-CTRL-9: verifier-side control checks now invoke the adapter with `control: false` and the exact fields of a counted `verify` call, so `job.json` no longer reveals that a verification is a control. The harness still logs it as a control and excludes it from measured rows. Prover-side controls (P1, P2, and `weakened_prover`) keep `control: true` (RFC-0005 rule 4). No existing adapter inspects the flag during `verify`, so no stored outcome changes.
- [RFC-0018](rfcs/0018-level-1-ladder.md) (amended 2026-11-15). SE-3b: sessions, control runs, and replacements count only when RFC-0014 classifies the run as release-eligible; ineligible runs are listed with their reasons and do not count as attempts. Because SASH's `2026-11-13-...-hosted-2` failed its host self-test (ST-SAMPLER, ST-JITTER), slot 2 reverts to its first session, Verify without weights becomes undecided (`not resolved`), and the row reads not passed (owner decision, Q21). SE-5: refusal records now include their upstream commit and apply only to rows at that commit; SASH's `eb95bfa` refusal was restored as that pin's record (Q22). SI-4: struck the inaccurate claim that a system proving a different statement could never pass the six checks, since a keyed hash computed over loaded weights passes all six. SI-4a and OR-6: a passing row receives a ranked position and counts toward the frontier only when the publisher's pinned statement confirms that an accept means the committed model's own greedy reply to the prompt (FlashProve states this in one sentence; SASH is read as stating it; no row moves; Q23, not yet decided by the owner). CH-1c: the board now records how many distinct modified inputs each control's trials sent.
- [RFC-0018 §The glyph](rfcs/0018-level-1-ladder.md#the-glyph) (amendment of 2026-11-13, adopted under the owner's request to update criteria from the research report, not yet decided by the owner; Q6 to Q14 document each choice): defines the five petals as Unforgeable, Weights hidden, Faithful model, Machine-checked, and No third party trusted, removing the rung-counting petal and renaming the trust petal. Each petal takes one of four steps (green in full, amber in part, amber in lesser part, or red) or not decided, with causes for red and hollow steps determined by decision tables (UF, MC, WH, FM, NT). `iproofs.glyph` computes the four statement petals directly from quoted facts in `systems/<name>/properties.yaml` (`properties/2`) with no hand-typed states. Unforgeable compares stated bound exponents against 128, 100, and 80 without computing a bits figure, and requires batch coverage plus a publisher statement or proof that the verifier program run implements the bound. Machine-checked remains hollow until a proof build is recorded at the pin with the pinned toolchain. Faithful model uses two thresholds derived from the rung's honest controls via FI-4's sign-flip test stored in `fidelity.json`, dropping to amber in lesser part if a required control did not run. Added GL-6 to GL-9: one fact per petal, separate evaluation of each petal, no summing across petals, and distinguishing unread files (hollow) from silence (red), with `release freeze` rejecting any release that has an unread statement petal. Updated `board/1` in place (RFC-0012 amendment of 2026-11-13). Facts based on a reviewer reading carry a note and mark the petal with `reading`. These rules were drafted with Claude, made by Anthropic, which publishes FlashProve (RFC-0018 §Conflicts of Interest).
- [RFC-0018](rfcs/0018-level-1-ladder.md) (owner decisions, 2026-11-10): introduced Level 1 in `levels/L1.yaml`. The site becomes a ladder of open-weights models (Llama 4 Maverick, then Llama 3.1 8B) using one fixed request across every rung (512 prompt tokens, 512 greedy reply tokens, every reply token checked, with prompts seeded from the first public randomness beacon round after level freeze), three cold sessions per row, six benchmark-run checks (Run, Model, Prompt, Reply, No weight file, and Fidelity) as the entry gate, a five-petal glyph tracking distance from a perfect prover (originally Unforgeable, Weights hidden, Faithful model, Any model, and Only the verifier trusted; read from `systems/<name>/properties.yaml`, lowered by failed checks, and never affecting rank), and one ranked metric within each rung: steady GPU-seconds per further proved reply divided by serving's GPU-seconds per reply at full load on a concurrency ladder. Nothing is ranked across rungs. Fidelity compares committed-copy replies against the publisher's 16-bit model in llama.cpp alongside honest and damaged controls via a paired sign-flip test, with KL divergence displayed but non-gating. Replaced RFC-0004 INV-SCOPE-5 with the release-group steady rule: on v0.1's four FlashProve H200 runs it yields 7.060, 7.082, 7.128, and 7.195 GPU-seconds per request where v0.1 published 5.746 (INV-SCOPE-5 had counted 119 steady requests for 96 produced). RFC-0016's documentation glyph, cross-model sorting, and RFC-0017 Part B no longer drive the site; v0.1 stays in the repository as an archived record and is not displayed.

Added per-request derived figures from stored runs (`tokens_covered_per_request` D-TPR, `gpu_seconds_per_request_<S>` D-GSPR-S, `cost_per_request_<S>` D-COST-REQ-S, `proof_bytes_per_request` D-BPR, and `verify_seconds_per_request` D-VSPR) with five new units and stored medians on every statistic. Refroze `releases/v0.1/index.json` adding 261 keys without altering any existing value, added three per-setup rows to system pages, forbade per-output-token metrics (INV-REQ-4), and laid out rules for future runs covering tasks, control coverage, proved-precision serving baselines, and per-verifier rows.
